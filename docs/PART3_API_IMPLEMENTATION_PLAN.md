# Part 3 implementation plan — FastAPI server

## What we are building, in simple terms

Parts 1 and 2 already do the work behind the scenes:

- Part 1 watches a video and produces a verdict.
- Part 2 saves the video, result JSON, debug pictures, and a searchable SQLite row.
- Part 3 gives those features URLs so a browser and, later, the Android app can use them.

An API is a set of agreed URLs and data formats. A client sends an HTTP request to a URL, the server calls ordinary Python functions, and the server returns an HTTP response—usually JSON. FastAPI is the thin translation layer between HTTP and our existing Python code. It must not contain the computer-vision logic itself.

For example, the phone will send a video and form fields to `POST /api/v1/analyze`. FastAPI validates the fields, temporarily saves the uploaded stream, calls Part 2's `create_analysis(...)`, and converts the saved result into public JSON. The request stays open while Part 1 analyzes the video, so the final verdict comes back directly; there is no background job or polling.

The API version is included in `/api/v1` so a future incompatible API can be introduced under `/api/v2` without breaking the first Android app.

## The APIs we will make

### 1. `POST /api/v1/analyze`

Purpose: upload and analyze a new video.

Request type: `multipart/form-data`, the same format a browser uses for a form containing a file.

Fields:

- `video` — required `.mp4` or `.mov` file.
- `label` — optional; one of `real`, `flat_printout`, `folded_printout`, `screen`, `bad_recording`, or `other`.
- `phone_model` — optional non-blank text.
- `attempt` — required positive integer, normally `1` or `2`.

Flow:

1. Validate the filename extension and form fields.
2. Stream the upload into a temporary file rather than loading the entire video into memory.
3. Call the Part 2 create-and-save workflow, which calls Part 1.
4. Apply the server-only rule before persistence: checker verdict `insufficient` plus `attempt >= 2` becomes stored verdict `review`.
5. Return the complete public result with HTTP `201 Created`.
6. Always remove the temporary upload, including after an error. The permanent Part 2 copy remains.

The response includes the ID, verdict, score, confidence, reason, metrics, pair details, processing time, submitted metadata, attempt, and API URLs for debug frames. It does not expose laptop filesystem paths.

### 2. `GET /api/v1/analyses`

Purpose: show analysis history, newest first.

Optional query parameters:

- `limit` — number of rows, default `100`, allowed `1–100`.
- `offset` — number of rows to skip, default `0`, minimum `0`.

This calls Part 2's `list_analyses(...)`. It returns lightweight summaries, not every pair metric. Public summaries contain the analysis ID, creation time, label, phone model, attempt, verdict, score, confidence, and a `detail_url`; internal file paths are omitted.

### 3. `GET /api/v1/analyses/{id}`

Purpose: retrieve one complete saved result.

This validates the UUID and calls Part 2's `get_result(...)`. A known result returns the same public shape as the upload route. An unknown ID returns `404 Not Found`.

### 4. `GET /api/v1/analyses/{id}/debug/{n}.jpg`

Purpose: retrieve one annotated JPEG generated by the checker.

This calls Part 2's `get_debug_frame(...)` and returns the file with media type `image/jpeg`. `{n}` is a zero-based integer. An unknown analysis or frame number returns `404`. Validation and Part 2's safe path resolution prevent arbitrary laptop files from being requested.

### 5. `POST /api/v1/analyses/{id}/rerun`

Purpose: run the original saved video again with the current threshold and phone settings.

This calls Part 2's `rerun_analysis(...)`. It creates and returns a new analysis with a new ID while leaving the original video, JSON, and database row unchanged. It preserves the original label, phone model, and attempt number, and applies the same server `review` rule before saving. An unknown source ID returns `404`; success returns `201 Created`.

### 6. `GET /`

Purpose: provide a small laptop testing page.

It returns `app/web/index.html`. The page contains the upload fields, calls `POST /api/v1/analyze` with browser `FormData`, and shows the verdict, reason, score, confidence, metrics, and debug images. It uses the exact same API the Android app will use, making it a useful end-to-end test rather than a separate implementation.

## Public response contracts

Create `app/schemas.py` with Pydantic models so FastAPI validates and documents responses:

- `AnalysisMetricsResponse` — the aggregate metric fields.
- `PairMetricsResponse` — the per-frame-pair measurements already emitted by Part 1.
- `AnalysisResponse` — one complete public analysis.
- `AnalysisSummaryResponse` — one history row.
- `AnalysisListResponse` — a list of summaries plus `limit` and `offset`.
- `ErrorResponse` — a stable error message shape.

Conversion helpers will turn `StoredAnalysis`, `AnalysisSummary`, and stored result dictionaries into these models. They will replace stored debug paths with URLs such as `/api/v1/analyses/<id>/debug/0.jpg` and will never return `video_path`, `result_path`, or `debug_directory`.

FastAPI will automatically expose interactive API documentation at `/docs` and an OpenAPI description at `/openapi.json`. These are generated from the routes, field declarations, and Pydantic schemas; we do not hand-write them.

## Step-by-step implementation

### Step 1 — Add server dependencies

Update `backend/pyproject.toml`:

- Add `fastapi`, `uvicorn`, and `python-multipart` as runtime dependencies.
- Add `httpx` to development dependencies for FastAPI's test client.

Keep `boxcheck` free of FastAPI imports. Only modules under `app/` may know about the web framework.

### Step 2 — Add a pre-persistence result policy seam

The existing `create_analysis(...)` and `rerun_analysis(...)` save the checker result immediately. Add a narrowly typed optional result-policy callback which runs after Part 1 returns and before `build_stored_analysis`, JSON writing, and SQLite insertion. The callback chooses the stored server verdict while leaving the standalone checker's `AnalysisResult` unchanged.

Implement an `app` policy function:

- If the checker verdict is `insufficient` and attempt is at least `2`, choose the stored verdict `review`.
- Otherwise preserve the checker verdict as the stored verdict.

Pass this policy from both analyze and rerun API workflows. Do not put the rule in `boxcheck`, because Part 1 must never return `review`. Test that JSON, SQLite, and the HTTP response all agree on the converted verdict.

### Step 3 — Define schemas and conversion helpers

Create `backend/app/schemas.py`.

1. Mirror the externally useful result fields with Pydantic models.
2. Type verdicts and labels using the existing enums where practical.
3. Add helpers for full results and list summaries.
4. Generate debug URLs by array position.
5. Exclude all internal paths.

Test conversion independently before adding routes. This catches accidental data leakage and response-shape drift early.

### Step 4 — Create and configure the FastAPI application

Create `backend/app/main.py` with an application factory such as `create_app(storage_settings=...)`, plus a normal module-level `app` for Uvicorn.

The factory lets tests use a temporary data directory instead of real `backend/data`. On startup, initialize the storage directories and SQLite schema. Give the service a title, version, and short description for generated documentation.

Add centralized exception mapping:

- Invalid request fields or UUIDs → `422 Unprocessable Entity`.
- Unsupported video extension or unusable upload → `400 Bad Request`.
- Unknown analysis/frame → `404 Not Found`.
- Oversized or checker-rejected video conditions should use the existing result semantics where Part 1 returns `insufficient`; genuine unreadable/corrupt input errors return `400`.
- Unexpected server/storage/checker failure → `500 Internal Server Error`, logged server-side without exposing paths or tracebacks to clients.

### Step 5 — Implement the upload endpoint

Add `POST /api/v1/analyze` first because it exercises the whole stack.

1. Declare `UploadFile` and form parameters.
2. Validate metadata before doing expensive work.
3. Copy the upload to a unique temporary file in bounded chunks.
4. Call the create-and-save workflow in a worker thread so blocking OpenCV and filesystem work do not freeze FastAPI's event loop.
5. Apply the review policy before persistence.
6. Convert the record into `AnalysisResponse`.
7. Delete the temporary file in `finally`.

Test success for labelled and unlabelled uploads, invalid label/attempt/extension, checker failure cleanup, and the second-attempt review rule.

### Step 6 — Implement read endpoints

Add the history, detail, and debug-image routes:

1. `GET /api/v1/analyses` delegates pagination to the existing store.
2. `GET /api/v1/analyses/{id}` loads and converts a full result.
3. `GET /api/v1/analyses/{id}/debug/{n}.jpg` returns a `FileResponse` only after Part 2 verifies the path.

Test empty and populated history, ordering, pagination boundaries, complete detail data, valid JPEG delivery, malformed UUIDs, and missing IDs/frames.

### Step 7 — Implement rerun

Add `POST /api/v1/analyses/{id}/rerun` and call the storage rerun workflow in a worker thread. The response is a new resource (`201`) with a new ID. Verify that the previous result is byte-for-byte unchanged, current settings are used, metadata is preserved, and the review rule is applied.

### Step 8 — Build the laptop page

Create `backend/app/web/index.html` using plain HTML, CSS, and JavaScript; no frontend build tool is needed.

The page will:

- Select a video and optionally enter label and phone model.
- Enter attempt number, defaulting to `1`.
- Disable the submit button and show progress text while the synchronous request runs.
- Clearly style `3d`, `flat`, `insufficient`, `review`, and errors.
- Render reason, score, confidence, aggregate metrics, and debug images.
- Handle non-2xx JSON errors cleanly.

Add a route test for the page and a lightweight assertion that it references `/api/v1/analyze`.

### Step 9 — Add integration and contract tests

Create `backend/tests/test_api.py` and use FastAPI's `TestClient` with temporary storage and a mocked checker for fast, deterministic tests.

The minimum contract suite covers:

- All six routes and their success status codes/content types.
- The documented response keys and absence of filesystem paths.
- Label, phone model, attempt, pagination, UUID, and frame-number validation.
- `insufficient` on attempt 1 and `review` on attempt 2.
- JSON/SQLite/HTTP verdict consistency.
- New ID and original preservation on rerun.
- Missing resources and internal failures.
- Temporary upload and partial-artifact cleanup.

Keep the existing Part 1 and Part 2 test suites running unchanged to enforce the architecture boundary.

### Step 10 — Document running and manually verify on Wi-Fi

Update `backend/README.md` with installation and launch commands:

```powershell
python -m pip install -e ".\backend[dev]"
python -m uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

Then verify:

1. Open `http://127.0.0.1:8000/` on the laptop and upload a real video.
2. Open `http://127.0.0.1:8000/docs` and exercise each API.
3. Find the laptop's local IPv4 address with `ipconfig`.
4. With both devices on the same trusted Wi-Fi, open `http://<laptop-ip>:8000/` from the phone.
5. If Windows Firewall prompts, allow Python/Uvicorn only on private networks.
6. Confirm the returned debug-image URLs load from the phone.

This server has no authentication or HTTPS and is intended only for local development on a trusted network. Those are separate production concerns, not requirements for this phase.

## Recommended implementation order and checkpoints

1. Dependencies and application factory.
2. Review policy seam, with storage tests.
3. Schemas/converters, with unit tests.
4. Analyze route, with end-to-end mocked-checker tests.
5. History, detail, and debug routes.
6. Rerun route.
7. Laptop page.
8. Full test suite, real-video smoke test, and phone-on-Wi-Fi test.

After checkpoints 2, 4, 6, and 8, run `python -m pytest backend`. Part 3 is complete only when all old tests and the new API tests pass.

## Definition of done

- A browser or phone can upload `.mp4`/`.mov` and receive one complete result in the same response.
- Attempt 1 `insufficient` remains `insufficient`; attempt 2+ is persisted and returned as `review`.
- History, detail, debug-frame, and rerun APIs work and return correct error codes.
- Public JSON contains useful URLs but no local filesystem paths.
- Rerunning creates a new result and preserves the original.
- The laptop page uses the public upload API and displays verdict and debug frames.
- `/docs` accurately describes the API.
- The complete backend test suite passes, and `boxcheck` still imports no FastAPI code.
